# 三位成员任务清单

本清单记录三位成员的责任、执行进展和尚未完成的工作。每项任务都必须留下可复查的代码、测试、运行产物或审核记录；本地受控模型不能代替真实模型服务，模拟测试不能代替远程 CI 或人工审核。

## 成员 A：评测、真实模型与最终裁决

A 负责回答“工具在真实数据上是否有效、结果是否可信”，并对跨模块争议作最终裁决。A 不直接修改 B 的静态分析逻辑，发现问题时提交可复现样例和期望行为。

**2026-09-20 执行进展：** A1 已完成工具辅助契约核对并新增 14 项通过的兼容性/失败处理测试，待 A 人工复核；A3 已准备独立标注及裁决模板，尚未正式冻结；A4 已建立四类验收证据表。详细结论、命令和缺口见 [A 的审查记录](a-contract-review.md)。A2 仍等待真实模型服务。以下各项完成标准继续适用，未收到的人工/远程证据不自动勾选。

### A1. 评审对外契约

1. 对照 `src/docsync` 的 CLI、配置和 Schema，逐项核对 `scan`、`patch`、`apply`、`schema`、`benchmark` 的输入、输出、退出码和失败状态。
2. 用一个 1.0 报告和一个 2.0 报告分别执行读取、报告生成和失败处理，确认旧报告能兼容读取且不会丢失关键证据。
3. 在 `docs/decisions.md` 或变更记录中写明每个不兼容行为；若发现契约问题，附最小复现命令和期望 JSON 结构。

完成标准：契约核对表无未解释项，兼容性测试可重复运行，所有变更都有对应测试或明确的拒绝理由。

### A2. 配置真实模型并完成小样本试运行

1. 在不把密钥写入仓库的前提下配置 endpoint、model 和 key；先用 3-5 个已人工确认的样例验证连通性、超时、限流和结构化响应。
2. 保存每次运行使用的配置版本、提交 SHA、请求数量、成功/失败数量、token usage、耗时和费用；密钥和敏感内容必须脱敏。
3. 再运行 `full`、`llm`、`no_alignment`、`no_verifier`、`no_static` 方法，确认 `PARTIAL`、拒答和服务失败不会被记为成功预测。

完成标准：`runs/` 下有可复查的原始结果和失败清单，真实请求数与模型 usage 对得上；服务未准备好时只记录阻塞，不伪造完成结果。

### A3. 冻结评测集并裁决指标

1. 与成员 B、C 分别独立复核 20 个受控种子的标签、证据类型和预期结论，不先看对方的标注。
2. 对分歧逐条写出裁决依据，冻结 manifest、标签、分组和版本 hash；新增真实样本时记录来源、许可和去重结果。
3. 运行统一 benchmark，报告 TP、FP、TN、FN、拒答、失败、零分母、Recall@K 以及各消融结果；不能只报告总体准确率。

完成标准：两名标注者的结果、裁决记录、冻结集 hash、命令和指标文件齐全，任何指标都能从固定 manifest 重跑。

### A4. 负责最终验收输入

收集 B、C 的结果后，更新 `docs/verification.md` 和 `docs/release-checklist.md`。必须单独标出本地已验证、真实模型已验证、远程 CI 已验证和人工审核已验证四类结论。

## 成员 B：核心扫描、静态事实与数据可靠性

B 负责回答“扫描到的代码和文档事实是否准确、定位是否可复现”。扩展能力时必须先定义不支持场景，并为每个拒答路径补反例测试。

### B1. 审核包、Schema 和仓库快照

**2026-09-28 执行进展：已完成。** 新增 B1 专项回归并收紧快照文件契约；专项测试 31 项、全量回归 143 项通过，另有 1 项 Windows 符号链接权限用例按设计跳过。Ruff、mypy、构建、隔离安装及安装版 CLI/Schema 核对均通过。命令、逐项证据和边界见 [B1 审核记录](b1-repository-review.md)。

1. 检查包安装、CLI 命令、Schema 2.0、配置未知字段拒绝、外键和证据关联校验。
2. 检查 Git blob、工作树显式模式、base/head 全量回退、文件过滤、大小限制、hash、CRLF、UTF-8 错误和符号链接诊断。
3. 对每项检查补充单元或集成测试；非 UTF-8 暂不支持时，测试必须确认返回明确诊断，而不是生成“扫描完成”。

完成标准：`pytest`、`ruff`、`mypy` 通过；安装后的 CLI 与源码 CLI 输出一致；所有不支持输入都有稳定的错误或拒答状态。

### B2. 扩展并验证静态事实

**2026-09-28 执行进展：已完成。** 修复继承/元类、动态字典键和重复定义的保守性缺口，新增可证明的直接/链式/相对重导出，并验证类型、`None`/`ABSENT`/`UNKNOWN`、参数绑定、接收者、歧义、证据溯源和稳定 ID。专项测试 22 项、全量回归 165 项通过，另有 1 项与 B2 无关的 Windows 符号链接权限用例按设计跳过；Ruff 和 mypy 均通过。详见 [B2 审核记录](b2-static-facts-review.md)。

1. 以现有默认值、调用绑定参数、接收者、顶层常量和字典规则为基础，逐项核对参数类型、`None`、缺失值和 `UNKNOWN` 的区别。
2. 任何跨文件导出、装饰器、重绑定、字典展开/更新或动态表达式的扩展，都先写“应拒答”的反例，再写支持用例，防止复杂 Python 被误判为一致。
3. 对每个新事实保留源文件、行号、字节范围、符号归属和 hash，并验证重复扫描产生稳定 ID。

完成标准：正例、反例和歧义样例均有测试；复杂动态语义不会被静默简化；报告中的证据可以回到固定源码 blob。

### B3. 对齐、规则和补丁回归

**2026-09-28 执行进展：已完成。** 补齐精确符号/参数归属、import 别名、源码链接、top-K 前歧义、重复调用、默认值/配置最小补丁、预览/hash/复扫、原子回滚、重复应用和签名人工处理测试；新增 canonical 行号校验与确定性 patch ID 校验。专项测试 15 项、全量回归 180 项通过，另有 1 项 Windows 符号链接权限用例按设计跳过；Ruff 和 mypy 均通过。三类规则报告及完整证据见 [B3 审核记录](b3-alignment-patch-review.md) 和 [审计样例](audit-samples/b3/README.md)。

1. 验证精确符号、参数归属、import 别名、源码链接、top-K 截断前歧义判断和重复调用稳定性。
2. 验证默认值/配置值的最小补丁、预览、哈希检查、复扫一致声明、原子写入、异常回滚和重复应用拒绝。
3. 对签名问题只生成证据和人工处理提示，不自动编造必选参数值；为每个规则记录一条可审计的报告样例。

完成标准：补丁只改目标声明，复扫能证明结果变化；过期、重叠、伪造行号或伪造 ID 的补丁全部被拒绝。

## 成员 C：文档证据、Action、合规与发布材料

C 负责回答“用户看到的说明、报告和发布材料是否清楚且可追责”。C 可以提出功能缺口，但不把尚未实现的自由文本 AI Claim 提取写成已支持能力。

### C1. 审核 Markdown 提取和证据报告

1. 用中英文正文声明、参数表、标题语境、代码围栏调用、源码链接、简单 import/实例别名和旧版/条件语境样例逐项复核。
2. 检查报告是否同时展示声明、代码事实、对齐依据、规则、忽略原因、到期日、阶段耗时、模型 usage 和失败原因。
3. 对无法明确归属的正文、复杂表格和任意自由文本，确认结果为拒答或不支持，而不是“一致”。

完成标准：每类证据都有人工抽查记录；JSON 和 Markdown 互相对应；人工能仅凭报告定位原始源码和文档位置。

### C2. 完成 Action 和 CI 验证

1. 检查 Action 只调用共享 CLI，使用固定第三方 SHA 和只读权限，不从目标 PR 安装工具。
2. 在本地复跑无冲突、文档漂移、无密钥、缺失 base、注入文本和模型超时六类场景，保存命令和结果路径。
3. 首次推送远程仓库后，运行 Windows/Linux CI 矩阵，记录工作流链接、提交 SHA、失败日志和修复结果；远程仓库为空前不得声称 CI 已通过。

完成标准：本地场景全部通过，远程工作流至少有真实运行记录，Action 示例中的可信工具 SHA 已替换为实际发布提交。

### C3. 完成人工标注、权利和发布审查

1. 与 B 独立完成 20 个种子的第二份标注，提交证据、标签、疑问和时间戳给 A 裁决。
2. 逐行审核 `compliance/third_party_resources.csv`、`installed_dependencies.csv`、`data_rights.csv` 和 `ai_assistance_log.csv`，补齐审核人、来源、许可证、用途和缺失项。
3. 确认 Apache-2.0 选择、原始资料不进入发布包、第二台设备复现步骤和材料匿名化；未确认的项目保持未勾选。

完成标准：人工标注和权利审核都有签名或可追溯记录，`docs/release-checklist.md` 只勾选有证据的项目，未完成事项保留阻塞原因。

## 共同执行顺序

1. B 先冻结当前扫描、报告和受控种子产物；C 同步准备证据抽查表和合规台账；A 评审契约并确认验收口径。
2. B、C 独立完成标注和本地验证后，A 裁决分歧并冻结评测集。
3. 模型服务可用后由 A 先做小样本试运行，再由 A 统一跑 Baseline 和消融；C 记录发布证据，B 修复可复现的扫描缺陷。
4. 远程 CI、第二设备复现、许可证确认和真实模型实验全部完成后，A 才能把发布清单标为完成。

每次提交都应写明：执行命令、提交 SHA、产物目录、通过/失败数量、未完成原因和下一位成员可直接执行的后续动作。
